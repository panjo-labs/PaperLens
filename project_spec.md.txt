# Evidence-first Research Assistant

## 1. Project Overview

### Project

Evidence-first Research Assistant

### Goal

Build an open-source, low-latency AI research assistant that helps students and researchers:

* Search academic literature
* Find relevant research papers
* Extract structured evidence from papers
* Compare studies
* Identify potential research gaps
* Detect conflicting findings
* Generate citation-grounded literature syntheses

The system should reduce the time required to move from a research question to a useful understanding of the existing literature.

### Primary Users

* University students
* Researchers
* Thesis/dissertation writers
* Academic project teams

### Initial Domain

The system should support general academic research, with particularly strong initial support for health and physiotherapy literature.

The architecture should remain domain-agnostic so that it can later support other fields.

---

## 2. Core Principle

### Evidence First

Every substantive factual claim generated by the system should be traceable to retrieved academic evidence.

The system should distinguish between:

1. **Direct evidence**

   * Information explicitly reported by a paper.

2. **Synthesis**

   * A conclusion formed by combining findings from multiple papers.

3. **Inference**

   * A reasonable interpretation derived from the available evidence.

The system must not present unsupported inference as established fact.

If the retrieved evidence is insufficient or conflicting, the system should explicitly communicate that limitation.

---

## 3. Core User Workflow

A typical user interaction should follow this process:

```text
Research Question
        ↓
Query Processing
        ↓
Academic Literature Search
        ↓
Paper Deduplication
        ↓
Paper Ranking
        ↓
Evidence Extraction
        ↓
Research Analysis
        ↓
LLM Synthesis
        ↓
Citation Validation
        ↓
Grounded Response
```

The user should be able to inspect the underlying papers supporting the response.

---

## 4. Required Features

### 4.1 Research Question Input

Users should be able to enter a natural-language research question.

Example:

> What is the effectiveness of exercise therapy for chronic low back pain?

The system should preserve the original research intent while generating useful search queries.

---

### 4.2 Academic Literature Search

Initial sources:

* PubMed
* Crossref

Search should:

* Query multiple sources where appropriate
* Run independent searches concurrently
* Normalize results into a common paper representation
* Handle API failures gracefully
* Apply sensible request timeouts
* Avoid exposing provider-specific details to the rest of the application

---

### 4.3 Paper Representation

All academic sources should eventually be converted into a common representation containing fields such as:

```text
id
title
authors
abstract
journal
publication_date
doi
source
source_id
url
```

Additional metadata may be added when reliably available.

---

### 4.4 Deduplication

The system should identify duplicate papers returned by different sources.

Preferred matching signals:

1. DOI
2. Provider-specific identifiers
3. Normalized title
4. Additional metadata when necessary

Deduplication should happen before expensive downstream processing.

---

### 4.5 Paper Ranking

Retrieved papers should be ranked before evidence extraction.

Ranking should initially use lightweight methods such as:

* Query relevance
* Title/abstract similarity
* Publication metadata
* Availability of useful abstracts
* Other inexpensive signals

Do not introduce a vector database or complex retrieval infrastructure unless evaluation demonstrates that it is necessary.

---

### 4.6 Evidence Extraction

For relevant papers, extract structured evidence where available:

```text
Study design
Population
Sample size
Intervention / exposure
Comparator
Outcomes
Main findings
Limitations
```

Missing information should be represented as unavailable rather than fabricated.

---

### 4.7 Citation-grounded Answers

The system should generate responses based on retrieved papers and extracted evidence.

Substantive claims should reference supporting papers.

The system must not invent:

* Papers
* Citations
* DOIs
* Study findings
* Statistics
* Authors
* Research gaps

Citations should only refer to papers actually retrieved during the current research workflow.

---

### 4.8 Study Comparison

The system should compare relevant studies across dimensions such as:

```text
Population
Study design
Intervention
Comparator
Sample size
Outcomes
Findings
Limitations
```

The comparison should help users understand why studies may produce different results.

---

## 5. Nice-to-have Features

These should be implemented only after the required workflow is stable.

### Research Gap Detection

Identify areas where the retrieved literature appears limited, inconsistent, or underexplored.

Gap statements must be cautious.

Preferred wording:

> "Based on the retrieved literature, relatively few studies examined..."

Avoid unsupported claims such as:

> "No research exists on..."

unless the system has genuinely established this.

### Contradiction Detection

Identify cases where relevant studies report different or conflicting findings.

The system should show the studies involved and explain the dimensions on which their findings differ.

### Literature Review Mode

Produce a structured literature synthesis across multiple studies.

Possible structure:

```text
Research question
Search scope
Key findings
Evidence by theme
Study comparison
Conflicting findings
Potential gaps
Limitations
References
```

### Citation Export

Potential formats:

* APA
* Vancouver
* BibTeX

---

## 6. Non-goals for the Initial Version

Do not implement these unless there is a clear project requirement:

* Autonomous multi-agent architecture
* Model fine-tuning
* Self-hosting a large language model
* Complex vector database
* Full PDF/OCR processing pipeline
* Complete thesis generation
* Zotero integration
* User authentication
* Collaboration features
* Knowledge graphs
* Kubernetes
* Microservice architecture
* Medical diagnosis
* Clinical decision-making

The goal is a strong working research assistant, not an unnecessarily complicated distributed civilization.

---

## 7. Technical Requirements

### Backend

* Python
* FastAPI
* Async/concurrent operations where appropriate

### Frontend

* React or Next.js
* Tailwind CSS or equivalent lightweight styling

### Academic APIs

* PubMed
* Crossref

### LLM

Use an open-weight model.

The LLM provider must be abstracted behind an application interface so the underlying model can be replaced without rewriting the research pipeline.

### Deployment

Deploy the application using:

* Render

### Communication

Use:

* REST APIs for standard operations
* Server-Sent Events (SSE) or equivalent streaming mechanism for generated responses where useful

### Storage

Start with lightweight storage such as:

* SQLite

Do not introduce a production database unless the application actually requires it.

---

## 8. Low-Latency Requirements

Latency is a first-class requirement.

The system should:

* Execute independent academic searches concurrently
* Avoid unnecessary LLM calls
* Perform cheap ranking before expensive processing
* Stream generated responses
* Use timeouts for external APIs
* Fail gracefully when one provider is unavailable
* Avoid unnecessary data transfers
* Avoid expensive infrastructure without measurable benefit

The implementation should optimize for perceived latency as well as total response time.

---

## 9. Reliability and Grounding

The system should prefer:

```text
Insufficient evidence
```

over:

```text
Confident unsupported answer
```

Every research response should ideally contain:

* Answer/synthesis
* Supporting evidence
* Citations
* Relevant source metadata

The system should clearly communicate uncertainty when evidence is limited.

---

## 10. Security

Never hard-code:

* API keys
* Access tokens
* Secrets
* Deployment credentials

Use environment variables.

Do not commit secrets to Git.

External API requests should use appropriate timeouts and error handling.

---

## 11. Testing Requirements

Tests should cover at minimum:

### Retrieval

* PubMed search
* Crossref search
* API failure handling
* Timeout handling

### Normalization

* Provider-specific results converted into the common paper schema

### Deduplication

* DOI-based duplicates
* Title-based duplicates

### Ranking

* Relevant papers ranked appropriately

### Evidence extraction

* Structured output validation
* Missing-field handling
* Invalid LLM output handling

### Citation validation

* Citations correspond to retrieved sources
* Unknown citation IDs are rejected

### Orchestration

* End-to-end research workflow

---

## 12. Evaluation

The system should be evaluated using a small fixed set of representative research questions.

Evaluate:

* Retrieval relevance
* Evidence extraction quality
* Citation correctness
* Groundedness
* Study comparison usefulness
* Gap detection usefulness
* Contradiction detection usefulness
* Time to first streamed response
* End-to-end latency
* Failure handling

Fluency alone is not a sufficient evaluation metric.

---

## 13. Implementation Priorities

Build in this order:

1. Project structure
2. Common paper schema
3. PubMed retrieval
4. Crossref retrieval
5. Concurrent search
6. Deduplication
7. Paper ranking
8. Evidence extraction
9. LLM provider integration
10. Citation-grounded synthesis
11. Citation validation
12. Study comparison
13. Contradiction detection
14. Research-gap detection
15. Streaming responses
16. Frontend
17. Render deployment
18. Evaluation and optimization

The first milestone should be:

> Given a research question, the backend reliably returns a clean and relevant list of academic papers.

---

## 14. Development Principle

Prefer the simplest implementation that satisfies the requirement.

Before introducing a dependency, database, service, framework, or architectural abstraction, determine:

1. What problem does it solve?
2. Is that problem currently real?
3. Can it be solved more simply?
4. Does it improve reliability or latency enough to justify the complexity?

Do not optimize for theoretical scale before establishing a reliable working system.
